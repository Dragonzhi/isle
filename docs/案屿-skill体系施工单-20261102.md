## 1. 背景：为什么做这件事

用户看到一个外部 skill `Haoo-7/agent-recap`（给本机所有 AI coding agent 装同一条收尾规则的安装器），认为案屿有可借鉴处。以下是评估后的结论，作为施工依据，**不需要重新评估**。

### 值得借鉴的三件事

| 借鉴点 | agent-recap 的做法 | 案屿的缺口 |
| --- | --- | --- |
| **适配器表化** | 20+ 个 agent 的落点写成一张表（agent / 落点 / 原生机制 / 证据档），新增一家只加一行 | 4 个入口硬编码在 `server/store.ts` 的 `skillTemplates()` 里，扩面要改逻辑 |
| **受管区块** | `<!-- recap:begin -->` / `<!-- recap:end -->` 只替换标记之间，外面一字不碰，撤除只删这块 | 案屿只能整文件拥有或整文件放弃，导致 README 里那条「安装不改 AGENTS.md、CLAUDE.md」 |
| **plan / status / remove** | `--dry-run` 打印计划、`status` 逐 agent 报告、`remove` 只删受管内容 | 只有「安装 / 补齐」，没有可观测面和撤回面 |

### 明确不借鉴的三件事

**不要照抄幂等覆盖。** agent-recap 能无条件重写，因为 recap 是无状态的格式约定，内容永不变。案屿的 `skills/isle/SKILL.md` 是有版本的规范，靠 `skills/isle/history.json` 的 sha256 判定「官方旧版 / 用户自有」。**这套版本判定是案屿的底线，不能为了「幂等」丢掉。**

**不要照抄作用域。** agent-recap 写用户级全局（`~/.claude/CLAUDE.md`），一次装全机器。案屿是项目级，只有登记过的项目目录才碰。S1 里的路径必须重新推导成项目级落点，**不能把 agent-recap 的路径清单直接平移**。

**不要复制它的源码。** 该仓库未声明许可证，本方案只借鉴结构约定，实现全部自行编写。

## 2. 硬约束（改坏了就是 P0）

以下行为在本次施工中必须完全保持，任何一条被破坏都算施工失败：

1. `TASKS.md` 是任务、交接摘要、工作留痕的**唯一**数据源，不新增第二套存储。
2. **不覆盖用户改动**：整文件类型的 Skill 文件，只有字节等于当前模板或等于 `history.json` 里某个已发布哈希时才替换，其余一律视为用户自有、永不覆盖。
3. 所有写入保持原文件的 **BOM 与换行风格**，未编辑部分字节不变。
4. 所有新建文件走 `ensureFile`（先写临时文件 + `fs.link` 硬链接发布，`EEXIST` 即失败不覆盖），**不要** 改成 `writeFile` 直写。

6. 服务只监听 `127.0.0.1`，写接口只接受 JSON 并校验 Host / Origin / 会话。新增 API 沿用现有 `json()` 与路由写法。
7. 改动走短生命周期分支 + PR，不直推 `main`。分支前缀：`feat/` `fix/` `design/` `chore/`。
8. 本轮涉及的 `TASKS.md` 任务与 `## 工作留痕` 跟着代码走同一个 PR，署名写实际参与者。

## 3. S1 · 适配器表化

**分支**：`feat/skill-adapters`
**目标**：把 4 条硬编码入口变成数据驱动的适配器表，并把「证据档」引入案屿。**本阶段不改变任何现有行为**，纯重构，做完 `npm test` 必须一条不差地全绿。

### 3.1 现状

`server/store.ts:92-104` 的 `skillTemplates()` 返回 4 条：

```ts
{ id: 'skill',    path: '.agents/skills/isle/SKILL.md',        data: skill }
{ id: 'metadata', path: '.agents/skills/isle/agents/openai.yaml', data: metadata }
{ id: 'entry',    path: '.claude/skills/isle/SKILL.md',         data: entry }
{ id: 'entry',    path: '.trae/skills/isle/SKILL.md',           data: entry }
```

`id` 同时被用作 `history.json` 的键，但 `entry` 重复出现两次，靠数组顺序区分。这是表化时要一并清掉的瑕疵。

### 3.2 目标结构

新建 `server/adapters.ts`：

```ts
export type AdapterKind = 'canonical' | 'entry' | 'marker';
export type Evidence = 'local' | 'docs' | 'unverified';

export type Adapter = {
  agent: string;      // 展示名，如 'Claude Code'
  key: string;        // history.json 的键，全局唯一，如 'claude-entry'
  path: string;       // 相对项目根，一律正斜杠，不带前导 ./
  kind: AdapterKind;
  evidence: Evidence; // 该落点的证据强度
  detect?: string;    // 相对路径，存在则视为此项目在用该 agent（仅用于推荐，不用于强制过滤）
  note?: string;      // 落点机制的简短说明，写入 status 输出
};
```

**`evidence` 的语义（照搬 agent-recap 的三档，但定义要说清）**：

- `local`：从已安装的该 agent 代码或行为中实际核实过落点，**默认参与安装**
- `docs`：官方文档记载，本机未实测，**默认参与安装但在 status 中标出「未实测」**
- `unverified`：仅传闻或推测，**默认不安装**，需要用户显式打开开关

这一档是 S1 的真正价值：把「不实测就不说实测」从文档自律变成数据结构。设计文档里那段「尚未实测四家 Agent 在真实会话中的发现与回写遵从率」的自述，从此有地方落。

## 4. S2 · 受管区块（marker）

**分支**：`feat/skill-marker`
**目标**：让案屿能往**用户已有的**规则文件里注入一段指针，且随时能干净撤除。这是本次施工价值最高的一段，也是风险最高的一段。

### 4.1 为什么值得做

案屿现在往项目里装 4 个独立入口文件，但 README 自己承认没测过这四家 agent 到底会不会发现它们。而 `AGENTS.md` 是 Codex、OpenCode、Cursor 等**确实会读**的约定文件。有了受管区块，「装到一家真被读到」替代「装到四家都没读」，杠杆完全不同。

### 4.2 注入内容

固定为以下块，**不要加长**：

```markdown
<!-- isle:begin -->
## 案屿（Isle）项目交接

本项目用案屿管理任务与交接记录。开工或收工前，先读取 `.agents/skills/isle/SKILL.md` 并按其规范执行；任务、交接摘要与工作留痕在项目根目录的 `TASKS.md`。
<!-- isle:end -->
```

要点：
- 用 `##` 而不是 `#`，避免抢占用户文档的一级标题
- 只写指针，不复制规范正文。规范正文仍只有 `.agents/skills/isle/SKILL.md` 一份（单一真源原则）
- 块内首尾各留一个换行，便于和用户内容分隔

### 4.3 写入规则矩阵（必须逐条实现 + 逐条测试）

| 情况 | 行为 |
| --- | --- |
| 文件不存在 | **不创建**。跳过，状态 `skipped`。理由：不替用户在没有约定的项目里凭空建 AGENTS.md |
| 文件存在，无 marker 块 | 追加到文件末尾：先补一个空行（文件末尾已有 `\n` 则不再补），再写块，末尾留 `\n` |
| 文件存在，恰有一个完整 marker 块 | **只替换 `begin` 到 `end` 之间**，块外一字不动。不比对 sha256（块内本来就是案屿地盘） |
| 文件存在，有多个完整 marker 块 | 全部替换为一份（收敛），并在 status 报一次 `warning` |
| 有 `begin` 无 `end`，或 `end` 在 `begin` 前 | **不写**，状态 `error`，message 写「标记不完整，请手动检查」。绝不猜边界 |
| 文件是符号链接 / 硬链接 | 现有 `noLinks` + `readRegular` 已拦，保持 |
| 撤销 | 删除 `begin` 到 `end` 整块，以及为它补的那个空行；块外一字不动。若删后文件只剩空白，**保留文件**（不删用户文件），状态 `skipped` |

**编码处理**（容易翻车，单列）：
- 读原字节，检测 BOM（`EF BB BF`）→ 写回时保留
- 检测主换行风格（`\r\n` 出现次数 > `\n` 的一半 → CRLF）→ 注入块用同风格
- 混合换行：以 marker 块所在位置之前的最近换行为准；无法判断时用 `\n`，并在 status 报 `warning`
- 块外的字节必须 `Buffer` 级原样保留，不要 `toString()` 全量重编码

**原子性**：沿用现有 `atomic()`（临时文件 + rename + 前置冲突校验）。读到的原字节哈希存进回调，写前再读一次比对，变了就抛 409。**这条必做**，因为用户很可能正开着编辑器改 AGENTS.md。

### 4.4 开关

> 决策点 B：默认开还是默认关。
>
> **建议默认关**，在项目 Skill 面板加独立开关「写入项目规则文件（AGENTS.md / CLAUDE.md）」。理由：这会修改被 git 跟踪、且属于用户既有约定的文件，与案屿现有「不碰 AGENTS.md」的克制一致；默认关等于把决定权留给用户，开了还要在界面上提示「这会修改 git 跟踪的文件」。
>
> 反方意见：默认关等于大部分用户永远不会开，S2 的价值就白做了。
>
> **请用户拍。** 无论选哪个，开关状态要记在 `settings.json`，随项目保存的是「是否已注入」而非「是否允许注入」。

### 4.5 落点范围

S2 只处理两个文件：项目根 `AGENTS.md` 与 `CLAUDE.md`。不要一次扩展到 `.cursor/rules` 等目录形式，那类走 S1 的独立文件路径，不需要 marker。

两个文件都存在时都要写，重复的指针不致命，且两家 agent 各读各的。

**如果文件里已经存在 `<!-- recap:begin -->`**（用户装过 agent-recap），两个块必须共存、互不干扰。写一个测试明确覆盖这条。

### 4.6 S2 验收

新增 `test/marker.test.ts`：

1. `marker block is appended to an existing rules file without touching user content` — 用户内容逐字节不变
2. `marker block replaces only its own region on reinstall` — 重装幂等，块外 mtime 与字节不变
3. `incomplete markers block the write and report an error`
4. `duplicate marker blocks collapse to one with a warning`
5. `remove deletes only the managed block and the separator it added`
6. `BOM and CRLF are preserved across install and remove`
7. `foreign marker blocks such as recap:begin coexist untouched`
8. `concurrent edit during install is rejected with 409`
9. `missing rules file is skipped instead of created`

手工验证：拿一个真实项目，手动在 AGENTS.md 里 marker 块外写几行自己的规则 → 安装 → 撤除 → 用自己的规则和原文 `diff`，必须零差异。

## 6. S4 · 暂不实施（留档）

以下是一条设计判断，**不在本次施工范围**，写在这里只作为后续讨论的起点。

`agent-recap` 的「每轮回复末尾两行状态」和案屿的「交接摘要 + 工作留痕」其实是同一件事的两个时间尺度：前者是单轮对话的收尾，后者是项目级的收尾。案屿现在把交接当离散事件，中间几十轮对话的全过程是丢失的。

若在项目级 Skill 里加一条「每轮实质回复末尾带一行极简状态，收工时汇总成一条留痕」，跨 Agent 交接就从「重建上下文」变成「读一条持续更新的状态流」。

**风险**：两行状态一旦套进每轮回复，很容易变成噪音，而且是不可撤销的噪音（写进对话历史）。若要做，建议先只在用户自己的项目里跑两周，实测它到底减少了交接成本还是又一层形式主义。**不要在没有实测的情况下写进规范。**

---

## 7. 施工顺序

```
main（先 git pull --ff-only）
 ├── feat/skill-adapters   S1  纯重构，测试全绿才合
 │     └── feat/skill-marker   S2  基于 S1，必须等 S1 合并
 │           └── feat/skill-status   S3  基于 S2
 └── 每个分支各自 PR，合并后删远端分支
```

S1 必须先合，因为 S2/S3 都要用 `Adapter` 类型。三阶段共用一个 `TASKS.md` 任务组，不要拆成三个互不相干的 PR 却各自改同一批任务条目。
